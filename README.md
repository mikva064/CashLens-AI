# CashLens-AI

CashLens-AI помогает проверяющему находить эпизоды в видео кассовых операций: показывает исходный таймкод, три выбранных кадра, короткий клип и основание для проверки. Сервис работает на компьютере пользователя; видео и кадры не передаются облачным AI.

Вход — видео `.mov` или `.mp4`. Выход — задача с результатом в веб-интерфейсе и JSON через HTTP API. Для трёх узких условий есть проверенные нормативные ссылки РК; ещё три типа видимых действий попадают в отдельный список наблюдений для ручного разбора. Найденный эпизод не устанавливает виновность или окончательную правовую квалификацию.

Модель — **Qwen3-VL-2B-Instruct**, локально на NVIDIA CUDA в 4-битном NF4. Веса **не дообучались**: проект добавляет выборку кадров, условия категорий, ограниченную генерацию JSON и проверку результата. Текущая ревизия — `observable-catalog-v2`. Независимая точность пока не установлена; состояние измерений приведено в [разделе оценки](#качество-и-проверки).

## Что проверяется

Точные условия содержатся в `config/rules.json` и `config/observations.json`. Для положительного вывода нужен весь обязательный видимый контекст, а не отдельный похожий кадр.

Нормативная основа трёх правил — Правила кассовых операций, утверждённые [постановлением Правления Национального Банка РК от 29.11.2019 №231](https://adilet.zan.kz/rus/docs/V1900019680). Проект проверяет узкие видимые признаки в банковском приёме наличных.

| Группа | Условие | Нормативная связь |
|---|---|---|
| Правило `cashier_leaves_during_service` | Работник фактически покидает рабочее место при продолжающемся приёме наличных. Поворот, вставание или работа с оборудованием внутри зоны исключаются. | №231, глава 2, параграф 2, пункт 22. |
| Правило `prior_receipt_cash_exposed` | Прослеженная партия завершённого приёма остаётся открыто на столе при следующем приёме; видна граница операций. | №231, пункт 20, абзац второй. |
| Правило `receipt_count_without_client` | После видимого ухода клиента продолжается пересчёт той же принимаемой партии; клиентская зона полностью видна. Внутренние пересчёты исключаются. | №231, пункт 20, абзац первый. |
| Наблюдение `cash_split_remainder_returned` | Полученные наличные разделены: часть помещена отдельно, остаток возвращён передавшему человеку. | Требуется проверка назначения и суммы операции. |
| Наблюдение `cash_receipt_id_not_visible` | В полностью показанном непрерывном приёме предъявление документа не наблюдается. | Цифровая идентификация и действия вне записи не исключены. |
| Наблюдение `received_cash_handed_other_person` | Одна партия прослеживается от посетителя к принимающему, затем к другому участнику. | Внутренняя передача уполномоченному сотруднику может быть допустимой. |

Наблюдения имеют `observation_id` и `review_reason`, без автоматического назначения нарушенной нормы. Открытая дверь, шкаф, сумка или перенос денег в сейф сами по себе не входят в активные категории. Система не определяет личность, полномочия, право собственности, умысел, проводки в АБИС или подлинность купюр по видео.

Источники и исключения: [проверенные нормы РК](docs/rk_rules.md), [каталог наблюдений и границы правовой оценки](docs/observation_rules.md), [формат расширения правил](docs/rules.md). [Дополнительные категории в sources.md](docs/sources.md) — черновик расширения и автоматически не активируются.

## Запуск на Windows

Нужны Python **3.12**, NVIDIA GPU с поддерживающим CUDA драйвером и место для полных весов Qwen. Команда `python` ниже должна выбирать Python 3.12; при необходимости передайте путь к нему через `-PythonExe`. Все команды выполняются из корня репозитория.

Первоначальная подготовка использует интернет для библиотек и весов:

```powershell
./scripts/setup_windows.ps1 -PythonExe python -WithModel
.venv/Scripts/python.exe -m pip install -e ".[data,service,model]"
if (-not (Test-Path -LiteralPath '.env')) { Copy-Item -LiteralPath '.env.example' -Destination '.env' }
.venv/Scripts/python.exe -m cashlens_ai.cli download-model --output local/models/qwen3-vl-2b
.venv/Scripts/python.exe -m cashlens_ai.cli doctor
```

Задайте свой `CASHLENS_API_KEY` в локальном `.env`. Существующий `.env` не заменяйте. Настройки и относительные пути — в [.env.example](.env.example). **Веса не входят в Git**: ожидается полный каталог `local/models/qwen3-vl-2b/` либо путь `CASHLENS_MODEL_DIR`. Модель загружается из локальных файлов; во время анализа загрузки из сети нет.

Запуск — двойной клик по `run.bat` или команда:

```powershell
./run.bat
```

`run.bat` создаёт `.venv` на Python 3.12 и устанавливает зависимости, если окружения ещё нет. При обновлении существующей среды повторите `.venv/Scripts/python -m pip install -e ".[data,service,model]"`.

Откройте [localhost:8000](http://localhost:8000), документацию API — [localhost:8000/docs](http://localhost:8000/docs). Дождитесь сообщения «Локальная модель готова к анализу» и `analyzer_ready: true` в `/health`, затем загрузите видео. ID сохраняется в адресе `/?job=...`, позволяя повторно открыть результат. После обновления кода обновите страницу через `Ctrl+F5`; ошибочная задача сама не загружается повторно.

`CASHLENS_ANALYZER=model` включён по умолчанию. Отсутствие весов, проверенного реестра или каталога наблюдений оставляет сервис `degraded` с причиной. Режим `mock` выбирается только явно и помечается как демо в интерфейсе и API; его результаты не измеряют работу модели.

## Сценарий проверки для жюри

После подготовки весов и запуска сервиса:

1. Откройте `/health`: проверьте `analyzer: "model"`, готовность, три правила и три типа наблюдений.
2. Загрузите локальное видео из разрешённого набора. Дождитесь завершённого результата или понятной причины `failed`; ошибку нельзя трактовать как отсутствие нарушений.
3. Для найденного эпизода откройте исходный таймкод, три кадра и мини-клип. Сопоставьте действие с условием категории и причиной ручной проверки.
4. Для нормативного срабатывания сохраните оценку проверяющего и проверьте изменение `/web/stats`. Скачайте JSON, сравните SHA-256 и откройте печатный отчёт.
5. Запустите автоматические тесты и отдельный прогон качества по протоколу ниже. Оценивайте работоспособность сервиса и качество распознавания раздельно.

## API и результат

Запросы `/api/v1/*` требуют `X-API-Key`, заданный через `CASHLENS_API_KEY`.

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/analyze` | `multipart/form-data`, поле `file` с `.mov` или `.mp4`; возвращает `job_id`. |
| `GET` | `/api/v1/jobs/{job_id}` | `processing`, `done` или `failed`; завершённый ответ содержит вердикт либо причину отказа. |
| `GET` | `/health` | Готовность, активные категории, параметры и ревизия обработки. |
| `POST` | `/web/jobs/{job_id}/feedback` | Отметка проверяющего по событию: `event_index`, `decision: confirmed/rejected`. |
| `GET` | `/web/stats` | Количество отметок `confirmed/rejected` по `rule_id`. |

Пример с условным локальным файлом:

```bash
curl -X POST -H "X-API-Key: <ключ>" -F "file=@video.mov" http://localhost:8000/api/v1/analyze
curl -H "X-API-Key: <ключ>" http://localhost:8000/api/v1/jobs/<job_id>
```

Сокращённый учебный пример ответов, без данных реальной записи:

```json
{"job_id":"example-job","status":"processing"}
```

```json
{"job_id":"example-job","status":"done","verdict":"no_violation","violations":[],"analyzer":"model"}
```

При найденном событии `violations[]` содержит `type`, `timecode_sec`, `description`, `evidence_frames[]` с исходными `timestamp_sec` и JPEG в `image_base64`. Нормативный источник включается в описание; сервис также добавляет `rule_id` и `source`. В завершённом ответе есть `analyzer`, `duration_sec`, `processing_time_sec`, `timings`. В очереди наружу возвращается `processing` с `stage: "queued"`.

Внутренний `AnalysisResult` содержит отдельные списки `violations[]` и `observations[]`:

| Найденное | Веб-интерфейс | Публичный API |
|---|---|---|
| Есть событие по проверенному правилу | `violation`, кадры, нормы, клипы; наблюдения при наличии показаны отдельно. | `done/violation` с нормативными событиями. |
| Есть только визуальные наблюдения | Завершённый анализ `requires_review`, кадры, клипы и причины ручной проверки. | `failed`, `failure_code: "requires_review"`, без вердикта. |
| Ничего не найдено | `no_violation`. | `done/no_violation`. |

`requires_review` — содержательный итог анализа, для которого не сформирован нормативный вердикт. Совместимая публичная схема предусматривает только `processing/done/failed`; `/api/v1/jobs/{job_id}/analysis` в таком случае возвращает HTTP 409. При смешанном результате API отдаёт `done/violation`, а веб показывает и наблюдения. Ошибка модели или превышение срока никогда не становятся отрицательным вердиктом. `no_violation` ограничен активным каталогом и не подтверждает соблюдение всех требований законодательства.

## Как устроен анализ

```text
Загрузка → SQLite-очередь → дочерний процесс с локальной Qwen
         → поиск кандидатов по окнам → уточнение последовательности
         → проверка структуры → исходные кадры + клипы + JSON
         → HTTP API и страница результата
```

1. Декодер применяет поворот из метаданных контейнера до уменьшения кадра. Исходные временные отметки сохраняются.
2. Грубый проход просматривает кадры с частотой 1 кадр/с в окнах 24 с с перекрытием 4 с. На каждое исходное окно выполняется один такой проход и не более одного уточнения найденных кандидатов.
3. Уточнение использует более детальные кадры и выбирает последовательность «до / действие / после» плюс кадр необходимого кассового контекста среди этой тройки. При нехватке видимого контекста модель должна воздержаться.
4. Генерация через `lm-format-enforcer` ограничена активными категориями и индексами кадров. Компактный ответ использует `k/b/f/a/c`; свободные подписи не генерируются. Описания берутся из фиксированных нейтральных шаблонов.
5. В `observable-catalog-v2` сама JSON-схема допускает только `b < f < a`, `c` из этой тройки, возрастающие исходные таймкоды и действие в окрестности кандидата. Последующая строгая проверка сохраняется. В результат попадают именно три выбранных исходных кадра; неверная структура вызывает ошибку, а не `no_violation`.

Смысл действий определяет та же локальная модель. Структурно корректная последовательность и готовый шаблон не являются независимым доказательством события. Редкая выборка может пропустить короткую передачу, границу обслуживания или скрытую зону. Особенно ограничены выводы об отсутствии действия во всей операции: три кадра не подтверждают её непрерывную видимость. При недостаточном контексте требуется просмотр исходного видео человеком. Близкие события одного типа могут объединяться через `AnalyzerConfig.merge_sec`.

Компоненты репозитория: `src/cashlens_ai/` — AI-модуль и контракт; `analyzer/` — подключение локальной модели или демо; `app/` — FastAPI, SQLite, воркер и FFmpeg; `web/` — интерфейс. Подробнее — [контракт интеграции](docs/integration.md).

## GPU, очередь и предел времени

По умолчанию включён сбалансированный профиль (`CASHLENS_PERFORMANCE_PROFILE=balanced`): кадры до 384 px при поиске и до 640 px при уточнении, до 8 кадров на уточняющий проход, лимит 131072 пикселя на изображение для модели. Частота поиска остаётся 1 кадр/с, окна — 24 с с перекрытием 4 с. Уменьшенные кадры и более короткая выборка могут пропускать мелкие объекты и короткие действия; точность нужно проверять на разметке.

`CASHLENS_GPU_DUTY_CYCLE` добавляет паузы между вычислениями. Это целевая доля работы, а не жёсткий предел показателя GPU: короткие пики 100% возможны. `CASHLENS_GPU_MEMORY_FRACTION` ограничивает бюджет аллокатора PyTorch после загрузки весов; память CUDA, драйвера и других программ в этот бюджет не входит. В примере `.env` используются 0.65 и 0.70; текущий локальный `.env` при обновлении не заменяйте. После окон и задач очищается неиспользуемая память, а веса остаются загруженными для следующего видео. Ограничение нагрузки может увеличить общее время, поэтому ускорение нужно оценивать вместе с настройками размера кадров.

Для более детальных кадров установите в `.env` `CASHLENS_PERFORMANCE_PROFILE=quality` и перезапустите сервис: 448/896 px, до 12 кадров на уточнение, 262144 пикселя на изображение. GPU-паузы и бюджет памяти сохраняются; значения `CASHLENS_MAX_EDGE`, `CASHLENS_REFINE_MAX_EDGE`, `CASHLENS_MAX_PIXELS`, `CASHLENS_MAX_REFINE_FRAMES`, `CASHLENS_SAMPLE_FPS` и параметров окон переопределяют профиль. Текущие эффективные настройки доступны в `/health` → `performance` и в интерфейсе. Диапазон обеих GPU-настроек — 0.1–1.0; увеличение до 1.0 убирает соответствующее ограничение доли.

Число незавершённых задач ограничено `CASHLENS_MAX_OUTSTANDING_JOBS` (по умолчанию 1, включая выполняемую). Переполнение сохраняет задачу как `failed/queue_full`; POST и последующий GET возвращают её ID и окончательную причину без вердикта. Пока модель загружается, новые файлы получают HTTP 503 с просьбой дождаться готовности. Видео обрабатываются последовательно.

Бюджет принятой задачи `CASHLENS_JOB_TIMEOUT` (270 с по умолчанию) считается с начала HTTP-запроса: время загрузки и очереди вычитается из времени обработки. Родитель следит за дочерним процессом независимо от генерации: при превышении помечает задачу `failed`, завершает дерево процесса модели и запускает новый обработчик. На Windows используется Job Object, на Linux — отдельная группа процессов. Повреждённый либо запоздавший результат не становится `done`. Сам приём медленного multipart-запроса этим watchdog не прерывается; если загрузка уже исчерпала бюджет, после её получения сервис сохраняет `failed/upload_deadline`.

В исправном дочернем процессе веса загружаются один раз и используются последовательно для следующих видео. Загрузка и повторная загрузка имеют отдельный предел `CASHLENS_MODEL_LOAD_TIMEOUT` (180 с по умолчанию). Во время перезапуска `/health` показывает `loading`; если подготовка модели не завершилась, сервис остаётся `degraded`, не выдавая ложных вердиктов. Кооперативные проверки внутреннего бюджета остаются дополнительным способом завершиться раньше жёсткого срока.

В `/health` доступны `rules`, `observation_type_count`, `observation_types`, `pipeline_revision`, `catalog_hash` и эффективный `performance`. Они позволяют воспроизвести состав каталога и настройки; хеш каталога не является метрикой качества.

## Кадры, клипы и отчёт

Для события сохраняются три выбранных исходных кадра и мини-клип до 3 секунд до таймкода и до 3 секунд после, с обрезкой по границам записи. `violations[].clip_url` и `observations[].clip_url` добавляются только в веб-ответ; публичная схема и внутренний `AnalysisResult` не содержат поля клипа. Веб также показывает MP4-превью исходного видео.

Кнопка «Распечатать отчёт» создаёт представление A4 / PDF с кадрами, основаниями и строкой подписи проверяющего. Отметки «Подтверждаю / Ложное срабатывание» хранятся отдельно в SQLite. `/web/stats` возвращает `{"by_rule":[{"rule_id":"...","confirmed":0,"rejected":0}]}`; блок «Отметки проверяющих» обновляется после сохранения. Это только статистика оценённых срабатываний: она не учитывает все пропуски и не даёт точность модели.

SHA-256 исходного файла считается по байтам во время загрузки. Сохранённый `/media/{job_id}/result.json` — отдельный неизменяемый артефакт; `result_sha256` относится к его точным байтам, а не пересобранному JSON. Внутри есть `input_sha256`, но нет собственного `result_sha256` или изменяемых отметок проверяющих. Веб возвращает оба хеша и `result_json_url`; скачивание отдаёт сохранённый файл. Изменение оценки не меняет артефакт и хеш. Для старых задач без него есть явно подписанный экспорт текущего ответа без подтверждённого SHA-256. Хеши позволяют сравнить байты и не подтверждают правильность события.

## Качество и проверки

**Независимая точность распознавания для текущей версии пока не установлена.** Известные ручные примеры использовались при настройке условий и запросов, поэтому их повторный прогон — reference-регрессия, не независимый holdout и не измерение юридической правильности.

| Проверка | `observable-catalog-v1`, 10 reference-видео | `observable-catalog-v2`, тот же reference-набор |
|---|---|---|
| Завершённый визуальный анализ / сбой | 5 / 5 | 10 / 0 |
| Совпадение наличия визуального кандидата, все видео; сбои считаются неуспехом | 2/10 (20%) | 4/10 (40%) |
| То же среди завершённых анализов | 2/5; 3 ложных срабатывания | 4/10; 6 ложных срабатываний |
| Хотя бы один предсказанный тип совпал с явно заданным типом, по видео | 0/3 | 1/3 (33,3%) |
| Среднее / максимальное время ответа | 71,0 / 150,6 с | 79,7 / 205,6 с |
| Ответ в пределах 300 с, включая ошибки и воздержания | 10/10 | 10/10 |
| Только наблюдения, без нормативного вердикта API | 1/10 | 5/10 |
| Независимый holdout | Не измерен. | Не измерен. |

Исправление v2 ограничивает структуру генерируемого JSON и не является дообучением или доказательством улучшения распознавания. Доли выше относятся к наличию **визуального кандидата** по ограниченной ручной разметке; их нельзя называть точностью определения нарушения закона. Ошибки не считаются чистыми видео. Отдельно нужно оценивать типы, локализацию, ложные срабатывания, пропуски, воздержания и время.

В v2 все шесть размеченных чистых видео получили срабатывания: улучшена устойчивость структуры ответа, но проблема ложных тревог не решена. Совпадение типа 1/3 не учитывает точность каждого дополнительного события и не заменяет событийную разметку. Текущая модель остаётся экспериментальной и не подходит для самостоятельного принятия решений о нарушении. Измерения получены на одной NVIDIA GPU в профиле `balanced`, с локальной 4-битной Qwen и настройками пауз/памяти 0.65/0.70; размер reference-набора — всего 10 уникальных видео. Локальные результаты прогонов находятся в `local/bench/reference-v1/` и `local/bench/reference-v2/` и не публикуются с исходными данными.

Установка средств проверки и автоматические тесты:

```powershell
.venv/Scripts/python.exe -m pip install -e ".[dev]"
.venv/Scripts/python.exe -m pytest -q tests
.venv/Scripts/python.exe scripts/smoke_model.py --model-dir local/models/qwen3-vl-2b
.venv/Scripts/python.exe scripts/check_local_service.py
.venv/Scripts/python.exe scripts/load_test.py --url http://127.0.0.1:8000 --output local/load-test.json
```

Последний полный прогон тестов для v2: **247 passed, 201 subtests passed, 2 skipped**. Эти числа характеризуют автоматические проверки программы, а не точность распознавания видео.

Регрессии проверяют JSON, допустимые категории, порядок и привязку кадров, воздержание, перестановку справочника, API, SHA-артефакт, очередь, жёсткий тайм-аут, завершение дерева процесса и восстановление. Синтетический smoke test проверяет загрузку модели; `check_local_service.py` требует работающий сервис. `load_test.py` отправляет пять синтетических видео одновременно и проверяет завершение каждого в пределах 300 с: нужен хотя бы один `done`, `failed/queue_full` допустим, другие ошибки дают ненулевой код выхода. Это проверки работоспособности и ограниченной очереди; они не измеряют точность на банковских видео или параллельную обработку пяти видео моделью.

Для измерения работающего сервиса используется отдельный протокол выборки:

```powershell
.venv/Scripts/python.exe scripts/benchmark.py --videos 'C:/dataset/videos' --suite reference_regression --output local/bench/reference
.venv/Scripts/python.exe scripts/benchmark.py --videos 'C:/dataset/videos' --suite clean_holdout --output local/bench/holdout
```

Ключ берётся из `CASHLENS_API_KEY` или локального `.env`. Нужны локальные `local/audit/manifest.json`, `local/annotations/reference-index.json` и `local/annotations/reference-protocol.json`; отсутствие протокола останавливает проверку. `--dry-run` проверяет выборку без чтения видео и запросов к серверу. Точные копии учитываются по SHA-256 один раз, неуверенные примеры исключаются. `reference_regression` использует известные примеры; `clean_holdout` — только оставшиеся SHA из протокола. После просмотра результатов такой набор нельзя повторно использовать как свежий независимый holdout для настройки.

Отчёт раздельно считает визуальные кандидаты, нормативные ответы API, воздержания `requires_review`, сбои и время. Типы проверяются только при явной разметке; общая положительная отметка не даёт эталона типа или времени. `--resume` продолжает только ту же выборку, ревизию пайплайна, каталог и настройки. Отчёты содержат ID, числа и таймкоды, без исходных имён, подписей и кадров.

Низкоуровневая оценка сохранённых результатов:

```powershell
.venv/Scripts/python.exe -m cashlens_ai.cli evaluate --manifest local/audit/manifest.json --predictions local/predictions.json --split holdout --output local/evaluation.json
```

Предсказания — массив `[{"sha256":"...","status":"done","result":{...AnalysisResult...}}]`; сбой имеет `status: "failed"`. Команда не применяет протокол исключения разобранных SHA автоматически. Пропуски и ошибки не становятся отрицательными ответами. Смещение к слабым точкам разметки — описательная величина, не официальная метрика локализации. [Подробная стратегия проверки](docs/observation_rules.md#проверка-качества), [план дополнительных съёмок](docs/filming-plan.md).

## Данные и прямой CLI-анализ

Подготовка данных работает без GPU. При необходимости создайте только такую среду: `./scripts/setup_windows.ps1 -PythonExe python`. Для последующего сервиса установите зависимости `.[data,service,model]`. Замените условные пути своими:

```powershell
.venv/Scripts/python.exe -m cashlens_ai.cli audit --labels 'C:/dataset/open_labels.xlsx' --videos 'C:/dataset/videos' --output local/audit
.venv/Scripts/python.exe -m cashlens_ai.cli review --manifest local/audit/manifest.json --output local/review.html
.venv/Scripts/python.exe -m cashlens_ai.cli analyze 'C:/dataset/videos/video_001.mov' --model-dir local/models/qwen3-vl-2b --rules config/rules.json --observations config/observations.json --output local/runs/job-001
```

Аудит сохраняет `manifest.json` с исходными аннотациями и SHA-256, `split.json` и `review.csv` с ручными полями; по умолчанию holdout содержит пять уникальных видео каждого класса. Ручные поля CSV сохраняются при повторном аудите. Все точные копии должны оставаться в одной части выборки; перекодированные версии и соседние фрагменты одной записи дополнительно группируют вручную. Использованные при настройке ручные примеры становятся reference/development. Неуверенная оценка или общая отметка без типа не заменяет событийную разметку.

`local/review.html` открывается непосредственно в браузере, читает оригиналы через file URL, не использует внешние ресурсы и не отправляет видео на сервер. Показывает development, позволяет разметить несколько событий, экспортировать JSON и импортировать для продолжения; неверные интервалы или несоответствующее видео не заменяют текущую разметку. JSON просмотрщика и ручной CSV пока не сливаются автоматически. Исходная точка не превращается в интервал; разные точки у одинаковой записи сохраняются для ручного разбора.

Прямому CLI-анализу нужен новый каталог результата; там сохраняются JSON и JPEG. Он работает в текущем процессе. Для жёсткого ограничения времени используйте HTTP-сервис с родительским наблюдателем.


## Docker с CUDA

Конфигурация находится в `Dockerfile`, `docker-compose.yml` и `.dockerignore`. Образ основан на [PyTorch 2.8.0 / CUDA 12.6](https://hub.docker.com/layers/pytorch/pytorch/2.8.0-cuda12.6-cudnn9-runtime/images/sha256-dab81780fd94483b67b4b5679cc0024939b08e48540d39476d284cb29002ed69), закреплён digest, содержит системный FFmpeg и зависимости `.[service,model]`. Пара версий `torch==2.8.0` и `torchvision==0.23.0` соответствует [официальной таблице PyTorch](https://pytorch.org/get-started/previous-versions/).

На Windows требуются Docker Desktop, Linux-контейнеры с WSL 2 и поддерживающий CUDA драйвер NVIDIA: [условия GPU в Docker Desktop](https://docs.docker.com/desktop/features/gpu/). На Linux требуется настроенный [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html). Конфигурация рассчитана на linux/amd64 и [одну NVIDIA GPU через Compose](https://docs.docker.com/compose/how-tos/gpu-support/).

Заранее скачайте полные веса в `local/models/qwen3-vl-2b/` и задайте свой `CASHLENS_API_KEY` в локальном `.env`. Существующий `.env` не заменяйте: Compose читает его, включая ваши `CASHLENS_GPU_DUTY_CYCLE=0.65` и `CASHLENS_GPU_MEMORY_FRACTION=0.70`. Веса не входят в образ и подключаются только для чтения. Если `run.bat` уже использует модель или порт 8000, остановите обычный сервис перед контейнерным.

Первая сборка и запуск — одной командой из корня репозитория:

```powershell
docker compose up --build -d
```

Сборка скачивает базовый образ и пакеты. После подготовки образа и весов повторный запуск выполняется без сборки:

```powershell
docker compose up --no-build -d
```

Сайт доступен на [127.0.0.1:8000](http://127.0.0.1:8000), API — на [странице документации](http://127.0.0.1:8000/docs). Дождитесь `analyzer_ready: true` в `/health`. Можно проверить состояние через `docker compose ps` и `Invoke-RestMethod http://127.0.0.1:8000/health`. Для другого порта задайте `CASHLENS_PORT` в `.env`.

Видео, кадры, мини-клипы, JSON и SQLite хранятся в именованном томе `cashlens-data`; `docker compose down` останавливает сервис и сохраняет том. Внутри работает один процесс Uvicorn и управляемый им дочерний процесс модели. `init: true` передаёт сигналы дочерним процессам; [healthcheck Compose](https://docs.docker.com/reference/compose-file/services/#healthcheck) допускает начальный период загрузки 180 секунд.

Приложение подключено только к [внешне изолированной сети `internal: true`](https://docs.docker.com/reference/compose-file/networks/#internal), а порт публикуется на [loopback-адресе](https://docs.docker.com/engine/network/port-publishing/). Веса загружаются с `local_files_only`, включены HF offline-флаги. Обычный внутренний bridge допускает связь с самим хостом; прокси для выхода через хост не настроены. [.dockerignore](https://docs.docker.com/build/concepts/context/#dockerignore-files) ограничивает контекст сборки исходниками и публичными правилами, исключая `.env`, видео, изображения, результаты и веса.

На текущем компьютере Docker CLI отсутствует. Конфигурация проверена статически, но сборка, GPU-доступ, публикация порта и исходящая сетевая изоляция здесь не проверены запуском. После установки Docker эти проверки нужно завершить на синтетическом видео; до этого контейнерный запуск не считается проверенным в этой среде.
